# 公共交付流程

适用于功能、修复、重构与规则整理。专题读取条件统一在 [项目入口](../CLAUDE.md)，不按角色编号重复跑多套链路。

## 1. 确定范围与验收

检查当前 Git 与相关交接，读现有实现和上下游。写清目标、已有能力、缺口、边界、风险和验证方法；确认按入口授权规则执行。

| 类型 | 实施前增加的检查 |
|---|---|
| 新功能 | 使用者、触发、正常/失败验收、接口字段与副作用；需要设计时先定方案 |
| 缺陷 | 保存失败证据，复现并定位，区分代码、环境、数据和外部依赖 |
| 重构/技债 | 列具体问题、影响、代价和优先级；确认保持的契约，必要时先补行为基线 |
| 文档/规则 | 完整读待改文件与引用者，列保留、迁移、删除依据；不顺带改业务实现 |

只对会改变产品、架构、外部副作用或范围的真实歧义澄清。明确方案后持续执行，测试选择按测试规范，不默认扩展为真实外部联调。

## 2. 实施与同步

按任务触发加载规范，复用既有能力，小步实施。同步名称、注释、调用方、测试、SQL、页面资源与有效文档；结构改动和行为变化分别核对。命中以下条件必须补对应检查，不等待用户另外提出审查要求；具体做法见 [调查与审查](investigation.md)。

| 变更触发 | 必须追加 |
|---|---|
| 新增/修改用户输入、页面表单、上传或实际外部回调 | 输入到危险操作的完整链路审查 |
| 鉴权、密钥、敏感数据或新信任边界 | 威胁建模与安全审查 |
| 新增/升级依赖 | 依赖与兼容性审查 |
| 新建/修改表、字段或索引 | 表结构与数据迁移审查 |
| 接口语义或字段变化 | 契约、兼容与调用方审查 |
| 根因指向数据库 | 执行计划与慢 SQL 分析 |
| 已上线行为改变或多方案取舍 | 明确代价，按授权确认结论并同步相应决策 |

## 3. 逐方法注释审计

Java 变更必须按 [Java 注释硬性规则](../rules/comments/comment-java.md) 检查本次完整变更方法，包含搬移、拆分方法及只改参数的方法；类首句、模板与真实职责另行检查。

| 方法 | 阶段数量与目的 | 方法说明 | 分段/编号 | 决策/兼容/生命周期说明 | 结果 |
|---|---|---|---|---|---|
| 文件路径#方法名 | 列实际目的与阶段 | 通过/缺失 | 通过/不适用及依据 | 按决策组列出及依据 | 通过/待修正 |

每个业务方法单独一行，不合并多个类或方法。“单阶段”“不适用”须写判定依据；跳过、成功、失败、降级等决策逐组核对，不能因有一条注释就整列通过。审计来自读代码，编译、注释数量或简单搜索不能替代。

Python 变更按 [Python 硬规则](../rules/comments/comment-python.md) 审计文件职责、类边界、方法四段、阶段编号、关键片段与兼容；其余脚本按开发规范检查，不套 Java 模板。纯文档变更说明代码审计不适用。

## 重构收尾的专有检查

明确要求重构收尾时，按顺序执行：读取可用 IDE/编辑器诊断并只修行为不变的告警 → 合并内部重复逻辑、保持公开签名 → 检查同主题一致性 → 行为回归 → 最终复核。工具不可用列明限制，不伪造“告警清零”。

同主题检查不是自动扩大范围的许可：已授权兄弟文件内只同步注释、顺序和空行，不改逻辑、字段、签名或日志；未授权时记录差异，不顺带修改。不把局部收尾升级为架构改造；长分支可评估 Map/枚举，但先保持语义，不为使用模式而改写。

## 4. 架构与差异复核

逐项核对真实分层、抽象价值、接口模型边界、资源所有权、事务/幂等和上下游契约；未涉及的项说明原因。再读最终 diff，从评审视角检查遗漏和新增风险，不把自己的实现意图当作证据。明确列出阻塞项与非阻塞项，阻塞先修正，非阻塞写处理或不处理原因；复核必须承接同一张注释审计表，不能只接受“已按规范检查”的声明。

### 模型归属验收

新增/移动模型或修改能力入出参时，按 [通用模型归属规范](../rules/engineering.md#模型归属) 中的目录表与跨层约束检查；项目既有实现状态另查项目记忆，不能把项目记忆作为第二套目录标准。验收时记录每个受影响模型的提供能力、所属层、包路径、调用方与转换边界。

- 能力契约的自有入参和返回模型是否由提供方定义并放在其 model。
- 领域业务模型是否统一位于 domain/model，是否混入数据库映射或厂商报文。
- 基础设施模型是否位于对应能力的 model，是否错误依赖上层领域/应用模型。
- 是否仍有 service/Client 旁平铺的模型、服务内部业务 DTO 或借 Map 绕过契约。
- 是否为必要隔离保留转换，且未泄漏凭据、破坏 ORM 扫描或调用签名。

发现不符先修正；现有代码未迁移时明确标记范围与缺口，不能只凭目录存在或编译成功宣称已符合。

## 5. 验证与交付

- 按 [测试规范](../rules/testing.md) 运行与风险相称的检查；按需复用或补充测试。存在未解决的新失败时不能宣称全部完成。
- 规则变更按 [维护检查](../maintenance.md) 验证链接、加载可达性、配置、失效引用、重复与冲突；机械检查通过后仍需人工核对语义和保留要求。
- 缺注释或审计先修正；其他阻断和无法运行的检查给具体原因，区分通过、失败、未测。
- 交付说明结果、证据和限制，更新必要交接；报告服务是否实际重启，不把源码修改当运行实例已更新。
