# 公共交付流程

适用于功能、修复、重构与规则整理。专题读取条件统一在 [项目入口](../CLAUDE.md)，不按角色编号重复跑多套链路。

## 1. 确定范围与验收

检查当前 Git 与相关交接，读现有实现和上下游。写清目标、已有能力、缺口、边界、风险和验证方法；确认按入口授权规则执行。

| 类型 | 实施前增加的检查 |
|---|---|
| 新功能 | 使用者、触发、正常/失败验收、接口字段与副作用；需要设计时先定方案 |
| 缺陷 | 保存失败证据，复现并定位，区分代码、环境、数据和外部依赖 |
| 重构/技债 | 列具体问题、影响、代价和优先级；确认保持的契约，必要时先补行为基线 |
| 文档/规则 | 完整读待改文件与引用者，列保留、迁移、删除依据；不顺带改业务实现 |

只对会改变产品、架构、外部副作用或范围的真实歧义澄清。明确方案后持续执行，测试选择按测试规范，不默认扩展为真实外部联调。

## 2. 实施与同步

按任务触发加载规范，复用既有能力，小步实施。同步名称、注释、调用方、测试、SQL、页面资源与有效文档；结构改动和行为变化分别核对。进入风险专题时按 [调查与审查](investigation.md) 补检查。

## 3. 逐方法注释审计

Java 变更必须按 [Java 注释硬性规则](../rules/comments/comment-java.md) 检查本次完整变更方法，包含搬移、拆分方法及只改参数的方法；类首句、模板与真实职责另行检查。

| 方法 | 阶段数量与目的 | 方法说明 | 分段/编号 | 决策/兼容/生命周期说明 | 结果 |
|---|---|---|---|---|---|
| 文件路径#方法名 | 列实际目的与阶段 | 通过/缺失 | 通过/不适用及依据 | 按决策组列出及依据 | 通过/待修正 |

每个业务方法单独一行，不合并多个类或方法。“单阶段”“不适用”须写判定依据；跳过、成功、失败、降级等决策逐组核对，不能因有一条注释就整列通过。审计来自读代码，编译、注释数量或简单搜索不能替代。

其他脚本按开发规范检查职责、参数、返回、异常与关键分支，不套 Java 模板。纯文档变更说明代码审计不适用。

## 4. 架构与差异复核

逐项核对真实分层、抽象价值、接口模型边界、资源所有权、事务/幂等和上下游契约；未涉及的项说明原因。再读最终 diff，从评审视角检查遗漏和新增风险，不把自己的实现意图当作证据。

## 5. 验证与交付

- 按 [测试规范](../rules/testing.md) 运行与风险相称的检查；按需复用或补充测试。存在未解决的新失败时不能宣称全部完成。
- 规则变更按 [维护检查](../maintenance.md) 验证链接、加载可达性、配置、失效引用、重复与冲突；机械检查通过后仍需人工核对语义和保留要求。
- 缺注释或审计先修正；其他阻断和无法运行的检查给具体原因，区分通过、失败、未测。
- 交付说明结果、证据和限制，更新必要交接；报告服务是否实际重启，不把源码修改当运行实例已更新。
