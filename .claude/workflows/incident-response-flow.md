# Workflow C —— 故障排查链（incident-response）

> 需要改代码时统一执行[代码变更流程](code-change-flow.md)；本文件只维护排查阶段，按当前阶段逐个加载角色，不要求创建多代理。

> 适用场景：本机或服务器上的报错、接口异常、后台任务失败或卡住、页面不可用、查询变慢。
>
> 触发关键词："报错 / 500 / 线上有问题 / 故障 / 排查 / 根因 / 慢 / 任务卡住"
>
> 核心原则：**先保留现场 → 用日志定位根因 → 需要时做慢 SQL 专项 → 修复走代码变更流程 → 有长期价值的结论才沉淀**。

---

## 1. 串联顺序

```text
14 log-rca                       日志根因
    ├─→ 16 slow-sql              根因指向数据库时
    └─→ 04 / 05 → 06 → 09        需要改代码时，按代码变更流程
```

---

## 2. 阶段定义

| 阶段 | Agent | 目标 | 验收 |
|---|---|---|---|
| 14 | log-rca | 用日志和异常栈还原失败链路，区分症状与根因 | 时间线 + 关键日志 + 根因假设及证据强度 |
| 16 | slow-sql | 执行计划、索引、扫描量分析 | 慢点 + 优化方案 + 写放大评估 |
| 04 / 05 → 06 → 09 | 修复与复核 | 按代码变更流程做最小修复并补回归测试 | 修复有回归测试，09 无阻塞项 |

---

## 3. 现场与证据

- 先记录现场：发生时间、环境（本机 / 服务器）、请求或任务标识、错误原文（脱敏）。
- 日志来源：本机命令行启动的看重定向的日志文件；服务器在部署目录执行 `docker compose -f docker-compose.yaml --env-file .env logs --tail=200 app`。
- 数据库状态用只读查询核对；排查中不直接改数据，确需修数据时先说明影响并经用户确认。

---

## 4. 严守边界

- **不做新功能 / 重构**：故障期间最小修改，修复走 04 / 05。
- **不越权操作服务器**：重启服务、改服务器配置或数据前，先说明影响并经用户确认。
- **结论沉淀**：可复用的排查经验经用户同意后写入 memory（环境类）或 rules（必须遵守的做法）；临时细节只写 HANDOFF。
- **风险升级**：按 [routing-policy.md](routing-policy.md)。

---

## 5. 触发示例

```text
"生成报告时报 500，看下日志"       → C
"诊断任务一直待执行，查下原因"     → C
"报告列表打开很慢"                 → C（追加 16）
```

---

## 6. 与其他 Workflow 的关系

| 关系 | 说明 |
|---|---|
| 与 Workflow B 区别 | B 是预防性扫描；C 是问题出现后的排查 |
| 与 Workflow F 区别 | F 是按计划回归接口；C 针对已出现的问题定位根因，F 中途失败时也借用 14 |
