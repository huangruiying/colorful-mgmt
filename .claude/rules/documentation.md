# 工程文档与交接

## 先取证再写

源码、调用方、SQL、运行配置及用户确认提供内容；分支和文件清单直接查 Git。只追问检索后仍缺失且影响结论的信息，不要求用户重新提供仓库已有内容。

已实现与拟议方案分别说明。负责人、排期、链接、外部状态未知时写“待确认”，不编造。用户只要方案时遵守项目入口的讨论边界。

文档落盘、项目范例与交接位置见 [项目工程记忆](../memory/project-practices.md)；通用写作要求在本文件维护。

## 接口说明

单独接口文档只面向调用方；HTTP、分页、登录与异常结构引用 [项目约定](../memory/project-conventions.md)，不定义第二套格式。每个接口单独成节，包含：

1. 名称、用途、方法、路径、调用方与鉴权。
2. Request JSON 示例及字段表：类型、必填、默认、单位、边界、枚举和业务语义。
3. Response JSON 示例及字段表；不使用 any 或“JSON 串”逃避定义。
4. 失败场景、HTTP 状态、detail 示例与处理建议。
5. 幂等、字段兼容和迁移要求；只展示增量时明确标记。

已有接口按实际契约写；默认字段只增不删，废弃前先标注。用户明确同意不兼容调整后才可删除或改变语义，并说明调用方、影响与迁移。接口路径用业务资源，不暴露表名和内部类名。

## 技术详细设计

面向研发、测试与上线负责人，保留以下章节及顺序；无变更写“本次无变更”，未知写“待确认”，不能用“暂无”掩盖未查证事项。

| 顺序 | 章节 | 必须说明 |
|---|---|---|
| 1 | 需求背景 | 动因、目标、边界值/空值语义、约束和相关资料 |
| 2 | 工程信息 | 服务、分支、实际仓库 |
| 3 | 实现逻辑 | 数据流、模块职责、关键变更文件与取舍 |
| 4 | 接口文档 | 按前节逐接口说明，可引用独立接口文档 |
| 5 | 库表设计 | DDL、迁移、旧数据和回滚边界 |
| 6 | 环境配置 | 配置名、默认值和用途；不放凭据 |
| 7 | 发版影响分析 | 每阶段的代码、库表/页面状态与影响；写清先改库还是先发代码 |
| 8 | 灰度顺序 | 有序步骤，每步操作、验证手段和失败停止点 |
| 9 | 测试关注点 | 条件 → 预期，覆盖正向、边界、异常和发布顺序 |
| 10 | 项目排期 | 功能点、负责人、复杂度、起止时间与进度，未知留待确认 |

边界值用行内代码标出字段与条件；兼容和降级写明触发条件。发版各阶段写出具体影响，测试关注点覆盖日志异常信号，JSON/SQL/配置代码块标语言，字段表紧跟示例。详细设计展示新增字段时明确增量口径，原接口完整契约不能省略。

标题体现模块与需求，项目的固定格式和参考文档以工程记忆为准；不能把范例中的实现结论照搬到新方案。

## 交付记录与 PR

重要任务留下可复核的结果、验证、风险、实例状态与下一步；具体交接、验收位置按项目工程记忆，临时结果不写长期项目决策。

需要 PR 时以具体问题和结果开头，说明改了什么、为什么、如何测试，以及配置、库表、兼容和回滚影响；简单变更不强制铺满模板。没有需求不生成 PR，不自动提交或发布。

PR 标题使用动词、业务对象和关键变化，70 字以内，不仅写 fix/update；不复刻 diff 或拼接 commit message。列清合入前剩余的测试、文档与非阻塞项处置。
