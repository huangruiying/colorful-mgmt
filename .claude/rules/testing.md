# 测试与验证规范

## 选择验证

- 新增业务规则、缺陷修复、关键重构、状态机、边界、重试、缓存策略或权限变化必须有行为回归；先检查已有测试，已覆盖时复用，不为每次修改机械新增测试。
- 缺陷测试覆盖原问题、修复结果与相邻边界；可稳定复现时先让测试失败，再验证修复。
- 纯注释、样式或简单搬移按风险选择 diff、编译、语法、引用与现有相关测试，不为字段赋值和低影响修改写镜像实现的测试。
- 完成相关必要检查后不无目的重复全量。用户要求全量测试不等于授权调用收费模型、对外发布或重启服务器，按明确范围选择验证层级。

实现与重构后的验证、评审都是默认执行阶段，不需用户另外提醒。新增或变化的行为缺少覆盖必须补测；已有测试明确覆盖时可复用，并说明覆盖依据。

## 分层与断言

单测验证业务规则、输入输出与状态；集成验证数据库、事务和适配边界；端到端验证页面或真实服务路径。真实请求执行方法见 [运行时回归](../workflows/runtime-api-test-flow.md)。

测试名表达“场景、动作、预期”，例如 `shouldRejectMissingPromptTemplate`；一个测试聚焦一个行为，断言业务结果与副作用，不仅断言非空或调用次数。测试数据语义清楚且可重复，不依赖共享脏数据、随机时间、执行顺序偶然性或任意 sleep；不锁死无关文案格式及不稳定中间过程。核心行为覆盖正常、非法输入、空值、边界和异常路径。

Mock 只替代不属于当前目标的协作者、高成本或外部副作用；不 mock 掉待验证的业务本身。数据库 SQL、事务与外键结论必须有对应真实边界的验证，H2 通过不等于 MySQL 已验证。测试夹具可复用，但不能把准备逻辑抽象到难以阅读。

Controller 的统一异常处理测试配置以项目约定为准。命令与运行环境按 [环境线索](../memory/runtime-env.md) 核对，不把历史失败视为本次可忽略的基线；归为既有问题须有当前基线或相应证据。

## 证据

记录实际命令、范围、结果和阻断，分别列出通过、失败、未测。测试替身通过、真实请求成功、后台产物完成与平台公开发布是不同结论，不能相互替代。不得删断言、放宽预期或改安全配置来制造通过。
