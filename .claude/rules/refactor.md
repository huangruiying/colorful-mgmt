# 重构规范

核心原则：

```text
可读性 > 可维护性 > 炫技
```

本文件只写重构专有的要求，其他专题以对应文件为准：命名 → `naming.md`，注释 → `comment.md` 与 `comments/`，日志 → `logging.md`，异常 → `error-handling.md`，分层 → `architecture.md` 与项目约定，生成范围与过度设计 → `code-scope.md`（§2.3~§2.4）。

---

# 硬性要求（速查）

```text
- 主流程线性化，像操作手册（§1）
- 方法职责单一，区分核心与非核心流程（§2）
- 方法尽量 10–30 行，禁止巨型方法、巨型类（§3）
- 禁止超过 3 层嵌套；业务失败用明确异常表达，禁止 return 分支散落（§4）
- 方法按调用链组织（§5）
- 禁止 utils 垃圾场（§6）
- 方法内复杂的逻辑，按业务或职能边界用空行分开
- 命名、注释、抽象分别以 naming.md、comment.md、code-scope.md 为准；禁止无意义注释和过度抽象
```

---

# 1. 主流程

主流程必须像"操作手册"：先做什么、再做什么、最后做什么。避免把大量 `if / for / while / try` 直接堆在主方法里。

---

# 2. 方法职责

一个方法只负责一个职责。校验、构造、持久化、通知等职责应拆成语义清晰的小方法。

## 2.1 核心流程与非核心流程识别

写代码或抽取方法时，必须先判断该逻辑属于核心流程还是非核心流程。

核心流程：

- 影响业务结果正确性
- 影响状态流转
- 影响报告、诊断结果、发布记录、导出文件等主产物
- 失败时必须阻断主流程

非核心流程：

- 进度日志
- 统计埋点
- 辅助诊断信息
- 非必要通知
- 临时文件清理等兜底动作

规则：

- 核心流程异常必须向上暴露，禁止吞掉或伪装成成功
- 非核心流程不得阻断主流程
- 非核心流程抽成方法时，方法内部必须自行 `try-catch`
- `catch` 后记录 `warn` 日志，说明非核心动作失败及关键上下文
- 禁止在主流程里散落非核心 `try-catch`，优先抽成语义明确的方法

---

# 3. 方法长度

方法尽量控制在 10-30 行。长逻辑必须拆分，拆分后的方法名要表达业务动作。

---

# 4. 提前终止与嵌套

业务失败优先使用明确异常表达，禁止 return 分支散落导致主流程被噪音污染；嵌套不超过 3 层。异常分类、catch 位置、日志边界见 `error-handling.md`。

---

# 5. 代码组织

方法按调用链组织，主入口在前，紧随其后的私有方法按调用顺序排列；禁止随机排列。

---

# 6. 工具类

工具类必须：无业务状态、无业务语义、可全局复用。

---

# 7. 生命周期与状态机

并发、监听、资源收尾等生命周期代码必须说明执行顺序，注释格式见 `comment.md` 与语言专项规则。
状态机、生命周期流转必须显式声明关键状态与迁移关系。
