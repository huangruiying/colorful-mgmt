# 接口文档生成规范

## 触发条件

当用户要求给前端、第三方或其他调用方提供接口说明时，进入本规范流程。

典型关键词：

- "接口文档" / "给前端接口文档" / "接口说明"
- "Request / Response" / "入参出参" / "字段说明"
- "新增接口" / "接口字段变更" / "错误说明"

---

## 适用边界

本规范只负责单接口或多接口的调用说明，不负责完整技术详细设计。

- 只写接口调用方需要理解的内容
- 不展开实现逻辑、库表设计、发布顺序、项目排期
- 如果用户要求"详细设计"、"技术方案"、"发版影响分析"，改用 `rules/tech-design-doc.md`

---

## 本项目的接口约定

以下是本项目的实际做法，写文档时照此描述，不另造结构：

- 成功时直接返回业务对象或列表，不包 `{code, message, data}`。
- 分页列表统一返回 `PageResponse`：`items`、`total`、`page`（从 0 开始）、`size`（1～100）。
- 出错统一返回 Spring `ProblemDetail`，前端读 `detail` 展示原因；状态码映射见[项目约定「接口异常响应」](project-conventions.md)。
- 除登录页外的接口都要求后台登录；写请求需带 `X-XSRF-TOKEN`（见项目约定「登录与访问控制」）。

---

## 生成前必须确认的信息

缺少以下信息时先追问，不要猜测填充：

1. 接口名称与业务用途
2. 请求方法与接口地址
3. 调用方角色（管理页面、第三方、内部服务）
4. Request 字段清单：字段名、类型、是否必填、语义、默认值、枚举范围
5. Response 字段清单：字段名、类型、语义、枚举范围
6. 失败场景及对应的 HTTP 状态码
7. 鉴权方式与权限要求
8. 兼容性说明（新增字段、废弃字段、版本差异）

---

## 文档结构模板

输出 Markdown。多个接口按"接口一、接口二……"顺序分别成节，不合并。

````markdown
# 接口文档

## 接口一：{接口名称}

### 接口基础信息

- 提供服务：{服务名}
- 接口地址：{METHOD} {path}
- 调用方：{调用方}
- 鉴权方式：后台登录会话；写请求带 X-XSRF-TOKEN

### Request

```json
{
  "field": "示例值"
}
```

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| field | string | 是 | 无 | 字段业务语义 |

### Response

```json
{
  "id": 12,
  "status": "SUCCEEDED"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| id | number | 记录 ID |
| status | string | 状态，枚举见下 |

### 失败响应

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "页码必须从 0 开始",
  "instance": "/xxx"
}
```

| HTTP 状态码 | 场景 | detail 示例 | 处理建议 |
|---|---|---|---|
| 400 | 参数非法或前置条件不满足 | 页码必须从 0 开始 | 按 detail 修正后重试 |
| 404 | 记录不存在 | 诊断报告不存在 | 刷新列表 |

### 兼容性说明

- 新增字段：
- 废弃字段：
- 版本差异：
````

---

## 写作规范

- Request / Response 必须使用 JSON 代码块，不允许写"json 串"占位
- 字段说明必须包含业务语义，不能只翻译字段名
- 枚举值、边界值、单位必须写清楚
- 新增字段只展示新增内容时，必须明确说明"仅展示新增字段"
- 接口地址禁止暴露表名、内部类名等实现细节

---

## 禁止行为

- 不得用 `data: any` 逃避字段定义
- 不得省略必填字段、失败场景、鉴权要求
- 不得编造不存在的接口、字段、状态码
- 不得把完整技术详细设计内容塞进接口文档
