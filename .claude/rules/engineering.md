# 开发与重构规范

## 修改前

- 读同类实现、上下游调用和数据契约，再确定最小修改点；先搜索已有工具类、依赖库、HTTP 客户端、线程池与 DAO 能力，能复用就复用。
- 只实现本次目标所需能力，必要校验、密钥隔离与失败处理属于实现责任；不为假想需求加开关、缓存、兼容分支、监控或扩展点。
- 抽象看职责、隔离价值和真实变化点，不用“只有一个实现所以禁止接口”“重复三次才抽取”等次数阈值替代判断。

- 用户提出方案时，先核对已有实现、调用方与数据来源并给出独立判断；重复配置、职责冲突或无实际收益的复杂度应指出，不默认顺着新增代码。
- 同一个事实只维护一处；可从已有类型推导的信息不新增数据库字段重复保存。拒绝空占位类、预留空方法、无调用路径的兼容入口和已有内部保证之外的重复空值防御。
- 新代码沿用当前模块的缩进、命名和错误处理风格；不夹带无关重命名、格式整理或周边优化。

## 职责与结构

分层的项目选择与注入方式按 [项目约定](../memory/project-conventions.md)，模型包路径和跨层调用统一遵守本文件「模型归属」。协议解析留在外部交互层。

- 主流程按业务顺序展开，用空行分隔阶段；有独立目的或重复规则才抽方法，避免长嵌套、复杂三元表达式和一个表达式串起组装、调用、解析多个动作。
- 方法尽量控制在 10–30 行，长逻辑按真实职责拆分；不为凑行数拆出纯转发方法。嵌套不超过三层，避免主流程散落失败分支；业务失败用明确异常，正常的空值、跳过、查询不存在按契约表达。
- 每个方法只承担一个清晰职责，校验、构造、持久化与通知按业务边界组织；同步接口与离线任务的触发、生命周期确有区别时保留，不机械合并。
- 主入口在前，私有方法按调用顺序组织；只在本次涉及的范围整理，不横向修改无关兄弟文件。
- 工具类应通用、无业务状态；业务规则留在所属模块，不堆进 utils。确有必要的业务协作者按职责命名。
- 用 Lombok 减少纯样板；不可变数据可用 record，但不为使用注解或 record 改变已有数据模型契约。

## 模型归属

本节是模型包路径与跨层调用的唯一规范来源，适用于采用 domain/application/infrastructure 分层的代码；路径均相对于项目基础包。模型归提供能力的一层所有，而非归调用者所有。

| 模型承担的职责 | 必须放置的位置 | 使用方式 |
|---|---|---|
| 领域服务自有的业务入参、结果和中间业务对象 | `domain/model/`，需要时按业务分子包 | 对应 Service 只负责行为，不能把业务 DTO 放在 service 包或其内部类 |
| 基础设施能力的自有入参、出参与辅助数据对象 | `infrastructure/<对应能力>/model/` | 由提供能力的一侧定义，领域服务调用时使用该类型 |
| 客户端请求、响应、回调与协议对象 | `infrastructure/client/<对应能力>/model/` | Client 处理外部协议，领域服务不承接原始厂商报文 |
| 数据库持久化实体 | `infrastructure/repository/model/`，可按模块分子包 | 只承担存储映射，不能替代领域服务自有模型向应用层透传 |
| 应用编排与接口输出模型 | `application/.../model/` | 领域层和基础设施层不依赖应用接口 Response |

应用接口输入 → 领域模型 → 领域服务；领域服务调用基础设施前，构造该基础设施的契约模型，调用后转回领域模型；应用层最后组装接口响应。字段转换显式进行，不以同字段为理由跳过必要边界。

应用与领域模型转换由应用边界负责，领域与基础设施契约在调用边界转换，数据库实体和外部厂商报文的内部映射由对应基础设施能力负责；不为转换新建无价值转发层。

- 领域服务引用基础设施契约模型只发生在调用该能力的边界，不等于要求将所有引用类型搬到 domain/model；基础设施契约也不能反过来引用领域模型作为入参或返回值。
- 同样禁止把模型放在 Client/Handler/Service 的实现目录、与能力类平铺，或在各个 service 子目录各自建 model。领域自有模型统一收在 domain/model 下，基础设施模型收在对应能力的 model 下。
- 数据库 Entity 不因“Service 用到了”而改放 domain/model；需要领域契约时建立真正归领域所有的模型，在持久化调用边界显式转换。简单 CRUD 也不豁免。
- 不强制每次方法调用都新建一对 Request/Response，也不包装每个标量。已有同职责、同所属能力的模型可复用；模型隔离的必要转换不得按“只有同名字段”删除。
- 数据模型只承载数据及其明确不变量，不承担网络、SQL、协议解析或业务编排。
- 既有 `repository/entity`、服务内部 DTO 或其他旧目录不构成例外。模型迁移须同步 package/import、能力签名、调用方、测试和 ORM 扫描，实际实施范围按任务授权执行。
- 对于自有结构化契约，必须按能力归属建模；不得用 Map/JSONObject 绕开归属要求。基础设施内部的临时报文组装按 [报文建模](channel-modeling.md) 执行。
- 通用规范的适用性与代码符合性分别核对。已有代码未整改不自动构成例外，也不能因规范已经写明就宣称实现符合。

## 状态、事务与资源

- 业务层决定状态、幂等与重复跳过语义，DAO 实现持久化，数据库唯一约束兜底并发。返回值区分新增、跳过和失败，只忽略已确定的重复冲突。
- 明确并发领取或重跑如何互斥；事务与外部副作用统一按下节边界处理。
- 明确共享资源所有者与释放顺序；使用方不创建重复池，不关闭 Spring 管理的线程池、连接池或共享浏览器资源。
- 表结构变更同步持久化模型、访问层与新库结构，已有库迁移保留数据、先检查且可重复执行；实际脚本与执行位置按 [项目工程记忆](../memory/project-practices.md)。

## 事务与外部调用

适用于采用 application/domain/infrastructure 分层、使用本地数据库事务的代码。事务按必须一起提交或回滚的数据库操作划定，不给整个层或整个用例统一套事务。

- 单个领域能力内的原子操作，由领域 Service 控制事务；跨多个领域 Service 且必须共同提交的纯数据库操作，由组织该用例的 Business 控制事务。基础设施封装 DAO 与存储映射，可保证自身持久化操作的原子性，但不能代替上层决定跨能力的业务事务边界。
- 同一原子操作中的下层写入须参与同一数据源、同一事务管理器所管理的事务；不能各自独立提交后声称整体可回滚。不同数据库或事务管理器不自动具备共同原子性。
- HTTP、远程模型调用及其他耗时外部交互默认放在数据库事务外；不能依赖本地事务回滚远端副作用。禁止为方便而用一个大事务包住“写库 → HTTP → 再写库”。
- 需要先占用业务状态再调用外部时，使用“短事务保存待处理状态 → 事务外调用 → 短事务保存结果”；失败、结果未知、恢复入口与重复执行策略按业务明确。纯查询可先调用再落库，但写入时仍须核对版本、状态或必要业务条件，不能把事务外旧查询当作并发保证。
- 远端写入或付费调用超时不等于未执行；根据真实协议选择幂等键、结果查询或明确的补偿，不能因本地落库失败自动重发已完成或结果未知的调用。协议无幂等、查单或补偿能力时报告限制，不编造保证，也不强行自动重试。
- 后续动作需要在进程崩溃后恢复时，将可恢复任务或待发送事件与业务数据在同一事务内落库，再由执行器处理；已有可靠任务机制能覆盖就复用，不默认引入消息队列或新 outbox 表。提交后回调、内存事件和线程池投递本身不提供持久可靠交付；恢复执行仍须防止重复副作用。
- Spring 代理事务须经代理调用；同类自调用不能假定 `@Transactional` 生效，需要时使用符合职责的独立 Bean 或编程式事务。不能靠换线程、挂起事务或 `REQUIRES_NEW` 假装释放外层事务的锁、解决远端一致性或保持整体回滚。
- 实施时列清事务入口、写入集合、回滚条件、外部副作用及恢复策略；验证覆盖回滚、并发和需要的恢复行为，沿用 [测试规范](testing.md) 的真实数据库边界要求。

技术依据：[Spring 事务传播](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)、[事务代理限制](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)、[事务事件](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)、[Outbox 说明](https://spring.io/blog/2023/10/24/a-use-case-for-transactions-adapting-to-transactional-outbox-pattern/)。这些机制说明不代表当前项目已实现可靠恢复。

## 范围与重构边界

重构前必须列清保持的接口、行为、性能与副作用，并具备可执行回归基线：已有测试能覆盖就复用，缺关键行为覆盖先补测；无法执行要记录阻断，不声称已守住行为。行为修改与结构整理分步核对差异；不要求另起无必要任务，但不能把行为变化称为纯重构。

改名按类内声明和注入类型调用定位，再靠编译查漏，包括 Mockito 链式调用；禁止对 `create`、`read`、`fail` 等通用词全局替换。检查完整生产者与消费者，包括测试、前端、SQL、资源版本和有效文档；接口路径及用户文案是独立契约，不随内部改名自动更改。

Python 的文件、类、方法四段与阶段注释按 [Python 硬规则](comments/comment-python.md) 执行。Shell、JS 辅助脚本写明用途、输入输出、副作用及关键分支，不引入其他业务系统的模板。
