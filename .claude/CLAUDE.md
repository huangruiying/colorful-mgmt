# colorful-mgmt 项目协作入口

本目录只服务当前仓库。规则定义要求，工作流定义执行顺序，memory 只提供环境线索。仓库名称与仍在使用的 `geo` 包、表、部署名称不要求一致，不凭名称删改实现。

## 协作与授权

- 使用中文，解释、页面文案和注释让人能看懂；页面文案用动作、对象和目的表达，技术术语只作补充。
- 先读 [当前交接](../.doc/HANDOFF.md) 的最新相关条目，检查 Git 状态、最近提交和相关 diff，保留已有改动。历史条目只在需要追溯时读。
- 超过 10 行的非简单修改，先说明目标、范围、风险和验证方法并确认；同一方案已确认后持续执行，不重复询问。用户只要求讨论或草案时不实施、不引导其进入编码。
- 不自动提交、推送、重置、清理或批量格式化；重启、改库、发布等副作用必须在已有授权内。没有授权时完成可审阅的准备后再确认。
- 工具角色只是检查视角，不因流程有多个阶段而创建子代理。多人共用目录时避免同时修改同一批文件。
- 用户明确要求才新增或修改长期记忆；“记住这个”视为授权。临时进度写交接，执行规范写 rules，模块决策写对应模块文件。
- 不生成后门，不关闭或绕过鉴权与安全校验；不把凭据、会话或带令牌的链接写进代码、文档、日志、报告与工具输出。

## 证据与冲突

- 工程要求以 [项目约定](rules/project-conventions.md) 和命中的模块决策为准；这些文件描述应遵循的约定，不等于实现已经满足。
- 已有行为先查当前代码的定义、调用方与数据来源。运行状态查进程、日志、数据库或真实接口；交接、图谱与 memory 都是可能过时的线索。
- 找不到接口、字段、配置、依赖或业务规则就标明未知，继续检索；仍影响决策才一次性问清，不补造“合理默认值”。外部协议、版本或工具能力不确定时查官方资料。
- 区分已观察事实、用户确定的要求与推测。来源冲突先报告差异，不能默默把规范改成现状，也不能声称缺失能力已实现。
- 规则须当前会话完整读取且未变化，或已完整注入才算加载；链接、搜索片段、截断输出不算。已读内容复用，变更后补读。

## 任务路由与按需读取

普通问答只读相关源码与证据；所有任务先读项目约定，环境相关任务再读 [环境线索](memory/MEMORY.md)。下列链接是唯一加载路由，不另建角色清单。

| 任务或改动 | 读取内容 |
|---|---|
| 功能、修复、重构、规则整理 | [公共交付流程](workflows/code-change-flow.md) |
| 新增或修改代码、分层与职责 | [开发规范](rules/engineering.md)、[命名](rules/naming.md) |
| Java 代码或注释 | [Java 注释](rules/comments/comment-java.md) |
| 日志、异常、线程、事务、外部调用 | [可靠性规范](rules/reliability.md) |
| 外部请求与响应建模 | [报文建模](rules/channel-modeling.md) |
| 测试实现或选择验证方式 | [测试规范](rules/testing.md) |
| 接口说明、详细设计、PR 描述 | [工程文档](rules/documentation.md) |
| 故障、慢 SQL、性能、安全、依赖审查 | [调查与审查](workflows/investigation.md) |
| 真实服务请求、启动与重启、接口报告 | [运行时回归](workflows/runtime-api-test-flow.md) |
| 规则或 hook 修改 | [维护与自动检查](maintenance.md) |

模块文件的触发条件和入口统一见项目约定「模块设计决策」。开始实施前简述适用规则和范围，不展开内部角色编号。

## 完成口径

报告结果、验证和限制，附可核对的文件或证据。源码已改、编译通过、单测通过、服务已重启、真实平台验证分别说明；未测、失败和无法运行不能写成通过。重要工作更新交接，不把历史快照复制成当前状态。
