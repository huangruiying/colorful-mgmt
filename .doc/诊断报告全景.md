# 诊断报告全景

状态：2026-10-17 与用户确认的报告结构；数据表、判定与汇总、接口与页面已落地，六个页签于 2026-10-18 全部接入（未做项见“判定与汇总”）。

## 分析口径

- 只分析成功的回答；调用失败、因输出上限截断（`finish_reason=length`）的结果不进入分析。
- 没有来源的回答不参与引用分析，但仍参与提及、推荐与态度分析。
- 各平台“引用”含义不同（豆包/OpenAI 为逐句引用，DeepSeek 为已打开网页，千问/智谱为搜索召回来源，文心为智能搜索网页），引用类指标只在同一口径的平台间比较。
- 以各模型的数据为主，跨模型汇总只作参考。

## 分析场景

同样是分析回答态度，问题类型和回答是否提到目标不同，分析对象与结论不同：

| 问题类型 | 回答提到目标 | 回答没提到目标 |
|---|---|---|
| 点名问题（直接问资产） | A 品牌口碑：模型怎么评价我们 | 几乎不会出现 |
| 非品牌问题（问品类、场景） | B 推荐态度：推荐我们时语气多强、带什么保留 | C 需求与期望：用户在意什么、对这类产品期待什么 |
| 对比问题（我们 vs 竞品） | D 相对评价：哪些方面赢、哪些方面输 | D' 竞品被评价的标准（未被列入对比本身就是问题） |

## 数据结构（2026-10-17 已落地）

报告手动点击生成；判定使用默认渠道（已启用渠道中分数最高者），实际所用渠道记录在报告上。每次生成一份新报告，重新生成不覆盖旧报告，结论可复现、可前后对比。

| 表 | 粒度 | 保存内容 |
|---|---|---|
| `geo_diagnosis_report` | 一次报告生成 | 所属诊断任务、生成状态、所在段（`stage`，2026-11-19 起）、第 2 段子步骤进度（`content_progress`，2026-11-19 起，只用于显示）、判定渠道快照、提示词版本、报告语言（2026-11-16 起，默认中文）、报告内容（指标、主要发现、优化建议、地域策略）、暂停或失败原因 |
| `geo_diagnosis_report_result_analysis` | 一次报告中的一条有效回答（`report_id` 关联报告） | 判定状态、品牌情感、描述是否准确；`brands`、`points`、`sources` 三个 JSON 数组；失败原因、是否人工修正 |

- 有效回答：诊断结果成功且结束原因不是 `length`（输出截断），创建报告时一次性建立待判定记录。
- 不重复保存可推导的信息：问题分组取诊断快照里的 `brandScope`（方案保存时已做品牌泄露检查）；引用口径由渠道快照中的策略决定；是否有来源、是否实际联网由诊断结果的引用和原始响应判断。这些在生成报告时计算并冻结进汇总。
- 品牌、观点、来源以 JSON 存储：生成报告时在内存中汇总即可；出现跨任务统计需求时再拆表。
- 自有域名暂取项目官网地址，做到 ⑤ 来源分析时再在项目档案中增加自有域名清单。

代码：`GeoDiagnosisReportEntity`、`GeoDiagnosisReportResultAnalysisEntity`；`GeoDiagnosisReportDao`、`GeoDiagnosisReportResultAnalysisDao`；领域服务 `GeoDiagnosisReportService.createReport`（锁定任务，校验任务已结束且有成功结果、无正在生成的报告，创建报告并建立待判定记录）；枚举 `DiagnosisReportStatus`、`DiagnosisReportStage`、`DiagnosisReportResultAnalysisStatus`、`DiagnosisBrandSentiment`。建表脚本 `021_geo_diagnosis_report.sql`，`022_rename_diagnosis_result_tables.sql`、`023_rename_diagnosis_task_tables.sql` 两次改名并保留数据；2026-11-18 报告两表再改为 `geo_diagnosis_report`、`geo_diagnosis_report_result_analysis`（页面上独立的对象用短名，从属表带所属对象前缀，已有库执行 `.doc/20261115_area_diagnosis/诊断报告表改名.sql`）。2026-11-19 报告表加 `stage`、`content_progress` 两列，状态加 `PAUSED`（已有库执行 `.doc/20261115_area_diagnosis/诊断报告分段执行.sql`）。现在的层级：任务 `geo_diagnosis_task` → 诊断结果 `geo_diagnosis_task_result`；报告 `geo_diagnosis_report`（`task_id` 关联任务）→ 回答分析 `geo_diagnosis_report_result_analysis`。新库直接使用 `001_init.sql`。

## 判定与汇总（2026-10-17 已落地，2026-11-19 改为分两段执行）

后台执行器 `DiagnosisReportWorker` 轮询报告（数据库会话锁 `:diagnosis-report-worker`，开关 `diagnosis.reports.enabled`，默认开启），优先续跑中断的 RUNNING 报告，其次领取最早的 PENDING 报告；已暂停（PAUSED）的报告不领取。报告分两段执行，`stage` 记录执行到或停在哪一段，从停在的段开始跑：

```text
冻结判定渠道（首次：默认渠道 = 已启用渠道中分数最高者；续跑、重跑：沿用快照中的同一渠道）
  没有已启用渠道 → 暂停（配好渠道后重试）；冻结的渠道被删除 → FAILED（重跑不换渠道，只能重新生成）
第 1 段 判定每条回答（stage = JUDGE），逐条待判定记录：
  ① 规则（ResultRuleAnalyzer）：来源归类 我方发布 → 自有域名 → 标题提到目标 → 标题提到竞品 → 其他，附平台名称
  ② 判定（ResultJudgePrompt，模板取自提示词管理，按报告冻结的版本）：一次调用拿全部字段，按问题分组只填适用部分；不联网，只依据回答原文；观点概括与维度名按报告语言书写，原文片段不翻译（v1 未规定语言，2026-11-16 起为 v2）
  ③ 校验：品牌名统一（目标统一为项目名，竞品简称归到预设名，对不上的为待确认产品）；观点原文片段去掉空白和 Markdown 符号后必须出现在回答中，否则丢弃
  ④ 保存成功或失败；单条失败不中断，接着判下一条，来源归类照样保存
  全部判完：有失败 → 暂停，原因如“判定失败 6 条：判定模型调用超时 4 条，判定模型限制调用频率 2 条”；全部成功 → 进入第 2 段
第 2 段 生成报告内容（stage = CONTENT），四步都跑完再看结果，每步开始、结束时更新子步骤进度（写地域策略时逐个地域报 x / y）：
  维度归一（1 次调用）→ 统计（ReportSummarizer 按页签调用各汇总类）→ 优化建议（1 次调用）→ 各地域提升策略（每个有机会的地域 1 次）
  全部成功 → summary 冻结 → SUCCEEDED
  归一、建议或某个地域策略失败 → 保存本次内容（维度保持原名，失败部分标记为生成失败）→ 暂停，原因如“写优化建议失败；写地域策略失败：美国”
  程序异常（如统计出错）→ 不保存内容 → 暂停，修复后重新生成
```

暂停后由用户在报告页选择，规则与状态切换都在 `GeoDiagnosisReportService`，执行器下次轮询领取：
- **重试**：停在判定段时调用重判，判定失败的改回待判定、成功的保留，判完接着生成内容；停在第 2 段时整段重新生成报告内容。
- **忽略失败继续**：停在判定段时失败的回答不计入依赖判定的指标，进入第 2 段（至少要有 1 条判定成功）；停在第 2 段时按已保存的内容直接完成（内容生成出错时不能忽略）。
- **已完成的报告**也可重判失败的回答或重新生成报告内容，跑完替换原内容，期间报告不能查看。
- 重新排队前检查同一任务没有别的报告在生成、冻结的判定渠道仍在；暂停的报告不算“在生成”，同一任务可以直接生成新报告。
- 服务重启或数据库异常中断时报告保持 RUNNING，下次轮询续跑当前段：判定段接着判剩下的，第 2 段整段重做。早期失败的报告（如全部判定失败）保持 FAILED，不能重跑。
- 第 2 段子步骤进度存在 `content_progress`（`{"steps":[{"key","status","detail"}]}`，四步 DIMENSION / SUMMARY / ADVICE / REGION_STRATEGY，状态 PENDING / RUNNING / SUCCEEDED / FAILED / SKIPPED），由执行器经 `DiagnosisReportContentProgress` 记录；只用于显示，失败的步骤同时拼成暂停原因，不参与重试判断。进度写库失败只记警告、不中断生成；完成或暂停时随结果一起写入；重新排队时清空。

**代码分工**（`report/` 下按段分包、段内按子步骤分包，2026-11-19）：第 1 段判定 `report/judge`（`ResultAnalyzer`、`ResultRuleAnalyzer`、`ResultJudgePrompt`）；第 2 段 `report/content`——1 维度归一 `content/dimension`（`DimensionPrompt` 组装提示词并解析、`DimensionNormalizer` 调用模型）；2 统计 `content/summary`：入口 `ReportSummarizer`，① `ReportOverviewSummarizer`、② `ReportVisibilitySummarizer`、③ `ReportBrandSummarizer`、④ `ReportCompetitorSummarizer`、⑤ `ReportSourceSummarizer`、⑥ 规则问题 `ReportIssueSummarizer`、⑦ `ReportRegionSummarizer`，共用 `ReportDimensionRanking`、`ReportAnswerFacts`、`ReportMetrics`；3-4 优化建议与地域策略 `content/tactic`（`AdvicePrompt`、`RegionStrategyPrompt` 组装提示词并校验输出、`TacticGenerator` 调用模型）。模型输出的 JSON 统一用 `infrastructure/client/llm/tools/LLMJsonOutputParser` 解析。

**summary 结构**：`sample`（有效回答、判定成功和失败数、带来源数、实际联网数、模型数、题数、最大采样次数、判定渠道、提示词版本）、`models`（每个模型一行：非品牌问题的提及率、推荐率、首推率、平均排名、问题覆盖率、稳定性；点名问题的品牌正面率；非品牌与对比问题的推荐份额）、`strength`（非品牌问题中提到目标时的推荐强度分布，点名与对比问题不计入）、`reservations`（目标的保留意见）、`criteria` 与 `concerns`（非品牌且未提到目标的回答中的选择标准与顾虑）；③ `brand`（点名问题：各模型正面/中性/负面数与描述准确率、`positives`/`negatives`/`sellingPoints` 排行、`factErrors` 清单）、④ `competitor`（`brands` 目标与各预设竞品在非品牌问题上的提及率、推荐率、首推率，`dimensions` 对比问题各维度胜负，`competitorReasons` 竞品推荐理由，`candidates` 新出现的同类产品）、⑤ `source`（各模型来源覆盖率及引用官网、我方发布、提到目标的第三方、提到竞品内容的回答占比，常引用平台，被引用的我方链接；判定失败的回答也参与）。排行按归一维度计数，每项最多 3 条原文示例。比率保留 4 位小数，分母为 0 时为 null。早期报告缺少某一部分时，对应页签提示点「重新生成报告内容」补上（2026-11-19 起由它代替原来只补缺失部分的「补全报告」，补全已删除）。

2026-10-18 补充：③ 增加负面来源（负面点名回答引用的平台）与卖点覆盖率；④ 增加 `headToHead` 同题胜率、`advantageScenes` 竞品优势场景；⑤ 增加 `competitorLinks`（推荐竞品的回答引用的网址）与 `contentGaps`（选择标准、顾虑下相关回答是否引用我方内容）。

**⑥ 优化建议与主要发现**：`issues` 由规则按固定阈值从 ②–⑤ 结果中挑出（提及率低于 30%、问题从未提到目标、竞品推荐率高于目标、保留意见/负面点/输掉的维度/内容差距各取前 3、错误信息、某模型从不引用我方内容、未设为竞品的产品出现 2 次以上），编号 P1…，带数字与证据。汇总后 `AdvicePrompt` 组装提示词，判定渠道调用一次生成 `advice`（findings、actions：类别 6 种、证据状态“回答明确表达 / 待验证推测”），只保留引用已知编号的条目；失败时 `advice.status=FAILED`，报告暂停在第 2 段，可重试或忽略失败继续。页面每条建议、发现与问题都可打开证据弹窗并继续查看原回答。

**筛选**：只做按模型筛选，作用于按模型分行的表格与带模型的问题；维度排行、链接与清单为全部模型合计。按问题组、意图、语言筛选需要按条件重算指标，未做。

未做：信息完整度中的“目标用户是否被说到”（判定提示词无该字段）。

**提示词**（2026-11-19 起在「基础配置 → 提示词管理」维护，同一页还管制题与内容优化的提示词）：报告的四个提示词（逐条判定、合并同义维度、优化建议、地域策略）存在 `geo_prompt_template`，按 `PromptTemplateKey` 取用，库是唯一来源，缺了那一步暂停并写明缺哪个。模板里 `{{变量名}}` 处由代码填入数据（`PromptTemplateRenderer` 一次扫描填充），各 `*Prompt` 类只负责填变量和解析输出，不访问数据库。保存总是新增一版：判定提示词在报告开始判定时冻结版本（`prompt_version` 记作 v + 版本号，初始模板沿用 v2 编号从第 2 版开始），续跑沿用、手动重判（含判定段的重试）换成最新版；第 2 段每次开始时读一次当前版本。初始模板就是改造前代码拼出的提示词，填入同样数据后逐字一致（2026-11-19 用 8 组样例核对）。

**判定渠道要求**：用不推理的快速模型。2026-10-17 实测：`qwen3.6-plus`（默认深度思考）每条 56–115 秒，超过服务统一 60 秒 HTTP 超时；`qwen-plus` 每条 10–34 秒。判定输出约 500–1000 token，渠道输出上限过小（如 1400）会被截断判失败。当时千问策略对每次调用都强制联网，上述耗时含搜索；2026-11-16 起判定、维度归一、建议、地域策略都不联网，实际耗时待重新实测。2026-11-16 起统一 HTTP 超时由 60 秒改为 600 秒（`http.llm.timeout-seconds`），起因是报告 #14 用 custom-gpt（非流式）判定时 6 条、维度归一和两个地域策略在 60 秒处超时。

**报告语言**（2026-11-16）：生成报告时选择，默认中文。观点概括、维度名、优化建议、⑦ 地域策略按报告语言书写；问题、回答、引用片段、来源、品牌名保持原文；规则拼出的问题标题、指标名与页面固定文字保持中文。重跑沿用报告记下的语言（旧报告为中文）。

**实测（6 条真实回答，两个被测模型、三类问题，判定模型 qwen-plus）**：全部解析成功；观点保留 31/36，丢弃的为跨段拼接引用；竞品名称全部归到预设名；汇总数字人工核对一致。

## 接口与页面（2026-10-17 已落地）

| 接口 | 说明 |
|---|---|
| `POST /diagnosis-reports/diagnosis-tasks/{diagnosisTaskId}` | diagnosisTaskId 为诊断任务 ID（geo_diagnosis_task.id）；可选请求体 `{"reportLanguage":"英语"}`，不传或留空为中文，最多 50 字；为一次已结束且有成功回答的诊断任务生成报告，返回 201 与判定进度；报告语言超长、任务未结束、已有报告在生成、没有有效回答时 400 并说明原因 |
| `GET /diagnosis-reports?diagnosisTaskId=&status=&page=&size=` | 报告列表，最新在前，含方案与项目名称（取自任务快照）、状态、判定进度；不含汇总 |
| `GET /diagnosis-reports/{id}` | 报告详情，含所在段 `stage`；已完成时含冻结的 `summary`，停在第 2 段暂停时含本次生成的内容，其他状态不返回内容 |
| `POST /diagnosis-reports/{id}/rejudge` | 重判没有判定成功的回答：已暂停或已完成、且有失败或待判定回答的报告可用，报告回到待生成、从判定段开始 |
| `POST /diagnosis-reports/{id}/regenerate-content` | 重新生成报告内容：停在第 2 段的已暂停报告或已完成报告可用，第 2 段整段重做 |
| `POST /diagnosis-reports/{id}/skip-failures` | 忽略失败继续：只对已暂停的报告可用；判定段进入第 2 段，第 2 段直接完成 |

页面 `history-report.html`（导航「诊断报告」）：
- 「生成诊断报告」按钮：选择一次诊断任务（只列已结束且有成功回答的任务）后生成。
- 诊断任务详情中，已结束且有成功回答的任务显示「生成报告」，跳转到报告页并预选该任务。
- 报告列表与详情在生成中每 3 秒刷新判定进度；列表在生成中和已暂停时注明所在段，状态筛选含「已暂停」。
- 未完成的报告在详情顶部显示两段进度（① 判定每条回答 → ② 生成报告内容，第 2 段下列出四个子步骤的状态与说明，如“合并同义维度 38 个维度合并为 21 个”“写地域策略 2 / 4”）和暂停、失败原因；列表里第 2 段生成中的报告带上当前子步骤；忽略失败后完成的报告顶部写明哪几步失败过；右上角暂停时为「重试」「忽略失败继续」，已完成时为「重新生成报告内容」与「重判失败的 N 条」（有判定失败时），已完成报告重跑前需确认。
